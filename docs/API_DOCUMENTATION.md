# PromptVault API Documentation

## Implementation Status

This document describes the API endpoints currently implemented in the backend.

**Implemented:** Health checks, authentication, prompt management, categories, favorites, and collections.

**Planned:** AI execution, execution history, dashboard, import/export, and dedicated prompt-version endpoints.

Base path: `/api`

## 1. API Conventions

- Request and response bodies use JSON where applicable.
- Protected endpoints require an authenticated session.
- Authentication uses the `pv_session` HTTP-only cookie.
- State-changing requests (`POST`, `PUT`, `PATCH`, and `DELETE`) must include the configured allowed `Origin`.
- State-changing requests must declare `Content-Type: application/json`.
- Requests with a body are subject to a 100 KB JSON body limit.
- Resources belonging to another user are generally treated as not found.
- Resource IDs are opaque strings generated by the application/database.

### Authentication

Register and login establish a session and set the `pv_session` cookie.

Protected endpoints require a valid session. The backend validates the session and identifies the authenticated user before accessing protected resources.

Logout deletes the current session and clears the cookie.

### Pagination

The prompt listing endpoint supports:

| Parameter | Default | Description |
|---|---:|---|
| `page` | 1 | Page number |
| `limit` | 20 | Number of results per page; maximum 100 |
| `search` | - | Case-insensitive search across prompt title and description |
| `categoryId` | - | Filter by category |
| `tag` | - | Filter by tag |

The prompt listing response includes pagination metadata.

## 2. Health Endpoints

These endpoints do not require authentication.

| Method | Path | Description |
|---|---|---|
| GET | `/api/health/` | Application liveness check |
| GET | `/api/health/ready` | Database readiness check |

### Liveness response

Returns HTTP 200 when the application is responding.

The response includes the service status, service name, timestamp, and request ID.

### Readiness response

Checks database connectivity using a database query.

- HTTP 200 when the database is available.
- HTTP 503 when the database is unavailable.

The response includes the readiness status and database connection status.

## 3. Authentication Endpoints

| Method | Path | Authentication | Description |
|---|---|---|---|
| POST | `/api/auth/register` | No | Register a user |
| POST | `/api/auth/login` | No | Authenticate a user |
| GET | `/api/auth/me` | Yes | Retrieve the current user |
| POST | `/api/auth/logout` | Yes | End the current session |

### POST `/api/auth/register`

Creates a user account and an authenticated session.

Request body:

```json
{
  "email": "user@example.com",
  "password": "a-secure-password",
  "displayName": "Example User"
}
```

Validation:

- Email must be valid and is normalized to lowercase.
- Password must contain 10 to 128 characters.
- `displayName` is optional and, when supplied, must contain 1 to 100 characters.

Success: HTTP 201.

The response contains the created user's ID, email, and display name. A session cookie is also set.

A duplicate email returns HTTP 409.

### POST `/api/auth/login`

Authenticates an existing user.

Request body:

```json
{
  "email": "user@example.com",
  "password": "a-secure-password"
}
```

Success: HTTP 200.

The response contains the authenticated user's details and sets the session cookie.

Invalid credentials return HTTP 401 with a generic authentication error.

### GET `/api/auth/me`

Returns the currently authenticated user's details.

Success: HTTP 200.

Authentication is required.

### POST `/api/auth/logout`

Deletes the current session and clears the session cookie.

Success: HTTP 204.

Authentication is required.

## 4. Prompt Endpoints

All prompt endpoints require authentication.

| Method | Path | Description |
|---|---|---|
| POST | `/api/prompts` | Create a prompt |
| GET | `/api/prompts` | List, search, and filter prompts |
| GET | `/api/prompts/:id` | Retrieve prompt details |
| PATCH | `/api/prompts/:id` | Update a prompt |
| DELETE | `/api/prompts/:id` | Delete a prompt |

### POST `/api/prompts`

Creates a prompt and its first version in a database transaction.

Example request:

```json
{
  "title": "Explain a programming concept",
  "description": "A reusable learning prompt",
  "template": "Explain {{topic}} using {{language}}.",
  "tags": ["learning", "programming"],
  "variables": [
    {
      "name": "topic",
      "description": "The concept to explain",
      "required": true
    },
    {
      "name": "language",
      "required": false,
      "defaultValue": "C++"
    }
  ]
}
```

Validation limits:

| Field | Constraint |
|---|---|
| `title` | 1 to 200 characters |
| `description` | Optional or null; maximum 1,000 characters |
| `template` | 1 to 50,000 characters |
| `categoryId` | Optional or null; must belong to the authenticated user |
| `tags` | Maximum 20 tags; each 1 to 30 characters |
| `variables` | Maximum 50 variable definitions |
| Variable name | Must match `^[A-Za-z_][A-Za-z0-9_]{0,49}$` |

Variable placeholders in the template are detected and validated against the supplied variable definitions. Invalid or inconsistent definitions are rejected.

Success: HTTP 201.

The created prompt is returned with its initial version.

### GET `/api/prompts`

Lists prompts owned by the authenticated user.

Supported query parameters:

| Parameter | Description |
|---|---|
| `search` | Search title and description |
| `categoryId` | Filter by category |
| `tag` | Filter by tag |
| `page` | Page number; defaults to 1 |
| `limit` | Page size; defaults to 20 and has a maximum of 100 |

Results are ordered by most recently updated first.

The response contains:

- `prompts`: the matching prompt records.
- `pagination`: page, limit, total result count, and total page count.

Search currently covers prompt titles and descriptions. Searching prompt template contents is not implemented.

### GET `/api/prompts/:id`

Returns the details of a prompt owned by the authenticated user.

The response includes:

- Prompt details.
- Category information.
- Current version and its variable definitions.
- Version summary information, including version number, change note, and creation date.

A prompt that does not exist or does not belong to the authenticated user returns HTTP 404.

### PATCH `/api/prompts/:id`

Updates prompt metadata or content.

Supported update areas include:

- Title.
- Description.
- Category.
- Tags.
- Template.
- Variable metadata.

Metadata-only changes do not create a new prompt version.

Changes to the template or variable metadata create a new version. Matching existing variable metadata is preserved where applicable when fields are omitted.

A supplied category must belong to the authenticated user.

Success: HTTP 200.

### DELETE `/api/prompts/:id`

Deletes a prompt owned by the authenticated user.

Success: HTTP 204.

A missing prompt or a prompt owned by another user returns HTTP 404.

## 5. Category Endpoints

All category endpoints require authentication.

| Method | Path | Description |
|---|---|---|
| POST | `/api/categories` | Create a category |
| GET | `/api/categories` | List categories |
| PATCH | `/api/categories/:id` | Rename a category |
| DELETE | `/api/categories/:id` | Delete a category |

### Category rules

- Category names are trimmed and must contain 1 to 50 characters.
- Category names must be unique for each user.
- Duplicate names return HTTP 409.
- Users cannot modify another user's categories.
- Deleting a category does not delete its prompts. Those prompts become uncategorized.

## 6. Favorite Endpoints

All favorite endpoints require authentication.

| Method | Path | Description |
|---|---|---|
| POST | `/api/favorites/:promptId` | Add a prompt to favorites |
| GET | `/api/favorites` | List favorite prompts |
| DELETE | `/api/favorites/:promptId` | Remove a prompt from favorites |

### Favorite rules

- A prompt must belong to the authenticated user before it can be favorited.
- Favorite records are unique per user and prompt.
- Adding an existing favorite returns HTTP 409.
- The listing is ordered by favorite creation time, newest first.
- Removing a favorite returns HTTP 204.
- Removing a favorite that does not exist returns HTTP 404.

## 7. Collection Endpoints

All collection endpoints require authentication.

| Method | Path | Description |
|---|---|---|
| POST | `/api/collections` | Create a collection |
| GET | `/api/collections` | List collections |
| PATCH | `/api/collections/:id` | Update a collection |
| DELETE | `/api/collections/:id` | Delete a collection |
| GET | `/api/collections/:id/prompts` | List prompts in a collection |
| POST | `/api/collections/:id/prompts` | Add a prompt to a collection |
| DELETE | `/api/collections/:id/prompts/:promptId` | Remove a prompt from a collection |

### Collection validation

| Field | Constraint |
|---|---|
| `name` | Required on creation; 1 to 100 characters |
| `description` | Optional or null; maximum 500 characters |

Collection names must be unique for each user.

The update endpoint requires at least one update field. A description can be set to null to clear it.

### Collection membership rules

- The collection must belong to the authenticated user.
- The prompt must also belong to the authenticated user.
- A prompt cannot be added twice to the same collection.
- Duplicate membership returns HTTP 409.
- Removing a nonexistent membership returns HTTP 404.
- Deleting a collection also removes its membership records through database cascade behavior.

These ownership checks prevent users from adding another user's prompts to their collections.

## 8. Error Handling

The backend uses centralized error handling and structured application errors.

The following HTTP statuses are relevant to the implemented endpoints:

| Status | Meaning |
|---|---|
| 201 | Resource created |
| 200 | Request successful |
| 204 | Request successful with no response body |
| 400 | Invalid request or validation failure |
| 401 | Authentication required or credentials invalid |
| 403 | Request origin is not allowed |
| 404 | Resource not found or not owned by the user |
| 409 | Duplicate resource or conflicting operation |
| 415 | JSON content type required |
| 429 | Authentication rate limit exceeded |
| 500 | Unexpected server error |
| 503 | Database readiness check failed |

Examples of implemented conflict conditions include duplicate registration email, duplicate category or collection name, duplicate favorite, and duplicate collection membership.

The exact error code and message depend on the route and error condition.

## 9. Security and Request Requirements

### Session handling

- Passwords are hashed using Argon2id.
- Session tokens are generated using cryptographically secure random bytes.
- Only a hash of the session token is stored in the database.
- The session is delivered through an HTTP-only cookie.
- The cookie uses `SameSite=Lax` and is configured as Secure in production.
- Sessions have a seven-day duration.

### Request protections

- Helmet applies HTTP security headers.
- State-changing requests must have the configured allowed Origin.
- State-changing requests must declare JSON content type.
- JSON request bodies are limited to 100 KB.
- Authentication routes use a rate limit of 10 attempts per 15 minutes per IP.
- Protected routes use authentication and user-scoped resource checks.

These controls do not mean that every planned production security measure is already implemented. See [Security Documentation](SECURITY.md).
